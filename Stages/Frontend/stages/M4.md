# M4 — Chatbots (Full CRUD + Settings Dialog)

## What was built

### chatbotApi (`api/chatbotApi.js`)
- **5 API functions** wrapping all admin chatbot endpoints:
  - `listChatbots()` → `GET /admin/chatbots`
  - `getChatbot(id)` → `GET /admin/chatbots/{id}`
  - `createChatbot(payload)` → `POST /admin/chatbots`
  - `updateChatbot(id, payload)` → `PUT /admin/chatbots/{id}`
  - `deleteChatbot(id)` → `DELETE /admin/chatbots/{id}`
- All return `{ status, chatbot }` or `{ status, count, chatbots }` from backend
- Uses `api` from `axiosInstance.js` — JWT handled automatically

### chatbotSlice (`store/slices/chatbotSlice.js`)
- **5 async thunks**: `fetchChatbots`, `fetchChatbotById`, `createChatbot`, `updateChatbot`, `deleteChatbot`
- **State shape**: `{ list: [], selectedChatbot: null, loading: false, saving: false, error: null }`
- **Reducers**: `clearSelectedChatbot`, `clearError`, `updateSelectedChatbot`
- `updateChatbot.fulfilled` updates both `list[idx]` and `selectedChatbot` in sync
- `deleteChatbot.fulfilled` filters `list` and clears `selectedChatbot` if deleted

### ChatbotList (`views/admin/Chatbots/ChatbotList.jsx`)
- **Card grid** — CSS grid `repeat(3, 1fr)` matching DocumentStoreList pattern
- **Card content** — bot name `1.3rem`, `StatusChip`, KB name (`IconDatabase` + caption), sessions count, LLM badge (`IconRobot` + `Chip` outline with `bot.llm_config.name`)
- **Three-dot menu** — `IconDots` + MUI Menu with 3 items:
  - **Edit** → opens `ChatbotSettingsDialog` pre-filled with that bot
  - **Open Chat** → navigates to `/admin/chat`
  - **Delete** → opens `ConfirmDialog` + dispatches `deleteChatbot`
- **Add Chatbot button** → opens `ChatbotSettingsDialog` in create mode (no existingBot)
- **Empty state** — IconRobot + text + CTA button
- **No click-to-navigate on card** — cards are not clickable (no detail page)
- **Fetches KBs** from `kbSlice` on mount for the KB dropdown inside the dialog

### ChatbotSettingsDialog (`views/admin/Chatbots/ChatbotSettingsDialog.jsx`)
- **Single dialog for both Create and Edit** — driven by `existingBot` prop
- **Opened from ChatbotList** — never navigated to as a standalone page
- **Full `maxWidth="md"` dialog** — matching UpsertionConfigDialog pattern
- **6 card sections stacked vertically** (same card styling as UpsertionConfigDialog):
  1. **Basic Info** — Name (required, autoFocus) + Description (multiline 3 rows)
  2. **Knowledge Base** — Select populated from `kbSlice` list, `MenuItem` for each KB, "None" option
  3. **LLM Configuration** — Provider select loaded from `/admin/components?category=chat_model` with `Object.entries()` conversion (same as M3 pattern), dynamic fields rendered from `/admin/components/:name/schema`
  4. **Chain & Memory** — Chain Type select (`ConversationalRetrievalChain`), Memory Type select (`buffer`, `summary`)
  5. **Instructions / Prompt Template** — Multiline 6 rows
- **Save builds payload**: `{ name, description, store_id, llm_config: { name, build_config }, chain_config: { chain_type }, memory_config: { memory_type }, prompt_config: { template } }`
- **Create mode** dispatches `createChatbot`, **Edit mode** dispatches `updateChatbot`
- **On save success** calls `onClose(true)`, which closes dialog and resets `editBot` to null

### App.jsx (`routes/`)
- `/admin/chatbots/:id` route now redirects to `/admin/chatbots` via `<Navigate replace />`
- ChatbotEditor import removed from App.jsx (file kept as redirect component for safety)

## Problems & solutions

### 1. Initial design had redundant create dialog + separate editor page
**Problem**: The first pass had a simple create dialog (name + description + KB) in ChatbotList, plus a separate ChatbotEditor page at `/admin/chatbots/:id` with the full form. User pointed out this was redundant — name/description appeared in both places, and the split 60/40 layout page was unnecessary overhead.
**Solution**: Consolidated everything into `ChatbotSettingsDialog` — a single dialog matching the UpsertionConfigDialog pattern. Both "Add Chatbot" and "Edit" use the same dialog (create mode vs edit mode via `existingBot` prop). No more editor page, no more navigation. The dialog has all settings in card sections stacked vertically.

### 2. `listComponents('chat_model')` returns an object, not an array
**Problem**: Same as M3 issue #1. `/admin/components?category=chat_model` returns `{ "ChatOllama": [...] }`, not an array. Calling `.map()` fails.
**Solution**: Applied same fix as M3 — `Object.entries(data || {}).map(([name, inputs]) => ({ name, inputs }))` in `ChatbotSettingsDialog.jsx`.

### 3. Build payload shape must match backend `CreateChatbotRequest` exactly
**Problem**: Backend's `CreateChatbotRequest` Pydantic schema expects specific field names: `store_id`, `llm_config`, `chain_config`, `memory_config`, `prompt_config` as dicts. Sending wrong keys causes 422.
**Solution**: Payload shape built carefully:
```javascript
{
  name: form.name.trim(),
  description: form.description.trim() || null,
  store_id: form.store_id || null,
  llm_config: form.llm_provider
    ? { name: form.llm_provider, build_config: form.llm_config }
    : null,
  chain_config: { chain_type: form.chain_type },
  prompt_config: form.prompt_template.trim()
    ? { template: form.prompt_template.trim() }
    : null,
  memory_config: { memory_type: form.memory_type },
}
```
- `llm_config.name` is the provider name (e.g. "ChatOllama"), `llm_config.build_config` contains the nested fields
- `store_id` is sent as `null` when no KB selected (not omitted)
- `null` values for optional fields are accepted by backend's Optional types

### 4. LLM config default values need `?? ''` not `|| ''`
**Problem**: When pre-filling the form from `existingBot.llm_config.build_config`, using `||` would overwrite falsy but valid values like `0` for temperature.
**Solution**: Used `?? ''` (nullish coalescing) instead of `|| ''` in field value bindings.

### 5. Chatbot Editor file still imported — must remove or redirect
**Problem**: App.jsx imported `ChatbotEditor` even though it was replaced by the dialog. Leftover import could cause build error if file is deleted.
**Solution**: Removed import from App.jsx, kept `ChatbotEditor.jsx` as a simple `<Navigate to="/admin/chatbots" replace />` redirect component so any lingering references resolve safely.

## What NOT to touch

- **`ChatbotSettingsDialog.jsx` — the `existingBot` prop** — This drives create vs edit mode. `null` = create, object = edit. Do NOT change this to a boolean flag; the dialog needs the full bot object to pre-fill fields.
- **`llm_config.build_config` shape** — The LLM config payload must be `{ name: "ChatOllama", build_config: { base_url, model, temperature } }`. This matches what the backend `CreateChatbotRequest` expects. Do NOT flatten `build_config` into the top level.
- **`chatbotSlice.js` — `updateChatbot.fulfilled` handler** — Updates both `list[idx]` and `selectedChatbot`. If you add new state fields, make sure both are updated.
- **Card aspect ratio `5/2`** — Matches DocumentStoreList. If you change it, adjust font sizes and chip sizes proportionally.
- **CSS grid `repeat(3, 1fr)`** — Same pattern as M3. Do NOT revert to MUI `<Grid>`.
- **`StatusChip.jsx`** — Any new status values (e.g. new chatbot statuses) must be added to the color map in both lowercase and title-case variants.
- **`Object.entries()` conversion for component schemas** — Every `listComponents(category)` call returns an object, not array. Always use `Object.entries(data || {})...`.

## Dependency on backend (frontend cannot fix)

- **Backend chatbot endpoint response shape** — `POST /admin/chatbots` returns `{ status: "created", chatbot: {...} }`, `GET /admin/chatbots` returns `{ status, count, chatbots: [...] }`. If response structure changes, update the thunks in `chatbotSlice.js`.
- **`chat_model` category must exist** — The LLM provider dropdown fetches from `/admin/components?category=chat_model`. If the category doesn't exist or has different naming (e.g., `llm` vs `chat_model`), update the category string in `ChatbotSettingsDialog.jsx`.
- **`chain_config` field behavior** — Backend stores chain config but `updateChatbot` currently only supports updating `chain_type`. If backend adds more chain config fields, extend the form in `ChatbotSettingsDialog.jsx`.
- **`listComponents` returns object** — Same as M3. The registry returns `{ Name: [inputs] }`, not an array. This is consistent across all component categories. The `Object.entries()` conversion is required everywhere.
